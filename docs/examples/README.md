# 示例：先看货，再上车

这里是两份示例，让你在真正动手之前，先看看用这个引擎**会拿到什么**。都是教学示意，结构与你实际得到的一致。

| 场景 | 输入（你给的） | 输出（你拿到的） |
|---|---|---|
| **正向**：一个想法 / 需求 → 完整方案 | [玩具剧场原始需求](../prd-toy-theater.md) 的「需求来源」或 [原始输入](../../evals/forward/toy-theater/input.md) | 见 [玩具剧场方案](../prd-toy-theater.md) |
| **反向**：一份代码 → 差距报告 | 一个学生写的「客服分诊机器人」项目 | [差距报告示例](差距报告示例.md) |

## 两份示例分别教你看什么

### 正向方案（玩具剧场）

重点看这几个部分，它们就是你之后每份方案都会有的：

1. **产品定位（一句话）**——引擎把你零散的想法收敛成一句可交付的定义；
2. **Step 1 需求拆解**——哪些是「明确」，哪些是「待确认」；
3. **Step 3 组件选型**——为什么选这几个、为什么放弃那几个；
4. **Step 4 架构设计**——七层架构图 + 工具清单 + 系统提示词草案；
5. **待确认清单**——答不上来就是风险点。

### 反向差距报告（客服机器人）

重点看这几个部分：

1. **一句话判定**——项目现在处于什么水平（只有雏形 / 有骨架缺机制 / 接近完整）；
2. **组件差距表（按优先级）**——P0 先补、P1 次之，每条都带「为什么需要它」和「去哪看」；
3. **建议下一步（按顺序做）**——直接告诉你先补什么、按什么标准补；
4. **五要素空位 + 六条验收标准**——从另一个角度看缺了什么。

> 提醒：差距报告是**静态扫描**得出的方向性判断，不是运行时验收；拿到报告后，照着 `sNN_xxx/README.md` 里的参考实现去补，补完再运行测试验证。
