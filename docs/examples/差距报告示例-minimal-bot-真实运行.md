## 它现在是什么

minimal-bot 目前是一个极小的单文件命令行助手（src/bot.py 为唯一入口，全项目仅 3 个文件），通过 Anthropic SDK 调用模型。它的用法是运维工程师输入一句自然语言，机器人据此调用 shell 执行命令，再把结果汇报回来。README 明确说明它可以执行删除文件、重启服务这类破坏性或高敏感操作。代码层面目前只看到模型调用（s01 强）与很弱的工具定义痕迹（s02 弱），没有护栏、审计、计划、记忆、调度等任何机制。项目整体更像一个可运行的原型，容错、可观测、可测试、可度量四项扫描均为 fail。

## 建议下一步（按顺序做）

1. **缺失：s03 权限系统** —— 先划边界，再给自由。生产级要点：白名单/黑名单、破坏性操作二次确认、审计日志、默认拒绝。参考 `s03_permission/README.md`。
2. **缺失：s04 钩子系统** —— 挂循环上，不写循环里。生产级要点：PreToolUse 可阻断、PostToolUse 可观察、异常不影响主循环。参考 `s04_hooks/README.md`。
3. **薄弱：s02 工具系统** —— 循环不变，工具可增。生产级要点：JSON schema 严格、参数校验、错误回传格式统一。参考 `s02_tool_use/README.md`。
4. **补齐验收：可容错** —— 工具失败、模型幻觉、超时、越权都有明确降级路径。
5. **补齐验收：可观测** —— 有日志、有指标、有轨迹数据。

## 需要项目作者回答的问题

1. 这个助手执行命令前是否需要用户二次确认？哪些命令（如 rm -rf、systemctl restart）属于必须先确认或直接拒绝的？
2. 是否存在命令白名单/黑名单或沙箱机制？执行权限是当前用户还是受限账号？是否会连生产环境？
3. 执行记录是否需要审计留痕（谁、何时、什么命令、什么结果）？需要保存多久、存在哪里？
4. 一次任务是否可能包含多条命令？如果是，是先出计划给用户看再执行，还是直接连续执行？
5. 衡量这个项目成功的可量化指标是什么（命令正确率、危险操作拦截率、平均响应时延、人工介入次数）？
6. 人机比是多少——是单个工程师本地使用，还是团队共用一个服务？交互是同步等待还是提交后台任务？
7. shell 输出很长时（如日志、进程列表）如何处理？是否需要截断、摘要或落盘？
8. 是否需要跨会话记住工程师的操作习惯、常用主机、历史决策？

10. 是否需要失败重试与错误兜底？命令执行失败或部分成功时，如何向用户汇报并恢复？
11. 【s05 任务规划】单次交付是否需要先列计划再逐步推进并跟踪进度（多轮、可中断、要汇报进展）？固定顺序调用几个工具不算。（现状：❌ 无）

13. 【s08 上下文压缩】会话是否很长、工具输出或日志量是否很大？（现状：❌ 无）
