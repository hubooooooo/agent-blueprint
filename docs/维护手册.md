## 常用命令

在引擎根目录运行：

```sh
.venv/bin/python -m blueprint plan idea.md -o out/my-plan
.venv/bin/python -m blueprint audit /目标项目路径 --prd prd.md -o out/my-audit
.venv/bin/python -m blueprint plan idea.md -o out/my-plan --resume
.venv/bin/python -m blueprint eval
.venv/bin/python -m blueprint eval --real
.venv/bin/python -m blueprint eval --real-audit --repeat 3   # 反向检查四道题，用 agent 真跑
.venv/bin/python tools/probe_tools.py [--model 模型名]         # 服务商能否调用工具
.venv/bin/python -m pytest -q

# 产品循环（blueprint/workspace.py）：工作区固定在 out/<产品名>/
.venv/bin/python -m blueprint init "产品名" "一句话点子" --plan
.venv/bin/python -m blueprint revise out/产品名 "新需求" [--no-plan]
.venv/bin/python -m blueprint verify out/产品名
```

`BLUEPRINT_OUT` 环境变量可以把输出根目录从 `out/` 改到别处（测试用）。`revise` 的做法是：快照 `PRD.md` 到 `prd/V{n}.md`、把「当前版本」升一号、在版本记录表追加一行、把新需求原文追加到「新增需求（待消化）」一节，然后以新 PRD 为输入 `--resume` 重推方案，并把前后 `plan.json` 的组件决策差异写进 `迭代记录.md`。`verify` 就是 `audit skeleton/ --prd PRD.md -o verify/` 的快捷方式，另加一条迭代记录。

`--mock` 为离线占位输出；`--model` 覆盖模型 ID；`--max-calls` 和 `--max-tokens` 限制新一轮运行的调用次数和 token 用量，不是金额硬上限。默认值 40 次、150 万 tokens（推导方案和检查项目默认都走 agent）；`audit`、`verify` 加 `--fast` 时为 16 次、40 万。网页界面推导用同一组默认值。

## 修改规则与模型

- **改规则**：同步修改选型规则、特征表和 `evals/forward/*/expected.json`，再运行离线评估。
- **加组件**：补齐组件说明、特征映射、扫描信号及测试；不要仅凭关键词数量认定功能完整。
- **改提示词**：模板使用 `str.format`，字面花括号写成 `{{ }}`。改完需做真实输出质量检查，不能只看 JSON 是否合法。
- **改模型**：维护者在 `.env` 配置 `ANTHROPIC_API_KEY`、`MODEL_ID`，自定义 Anthropic-compatible 网关使用 `ANTHROPIC_BASE_URL`。环境变量优先于 `.env`。不要将密钥复制到手册或分发包。
- **失败续跑**：同一任务使用同一输出目录加 `--resume`。缓存核对输入、源码摘要、模型、提示词、schema 和上游结果，变更或损坏时重跑；写入使用原子替换。

## 验证边界

- 离线题库覆盖 3 个正向案例和 4 个反向案例；`eval --real` 只测正向需求拆解，`eval --real-audit` 用 agent 完整跑反向四题。完整正向方案仍需真实验收。
- 反向检查默认由 agent 读代码核实组件（见下文「反向检查的 agent」）；`--fast`、mock、agent 失败时用扫描结果。
- 扫描为正则启发式；业务代码命中至少 2 个文件或 4 行为 strong，1 个文件为 weak。文档和测试描述不计为实现，扫描跳过符号链接和依赖目录。关键词会误报和漏报，`evals/reverse/keyword-only`、`no-keyword` 两题专门演示这两种情况。
- 静态分数不能证明能力已集成，也不能替代运行测试；非 Python 入口与调用关系识别有限。
- 正向审稿失败会重写一次；审稿是同一模型的另一次调用。反向复核的输入覆盖仍需加强，尤其是用户 PRD 与反推意图不一致时。
- 真实请求超时 120 秒，关闭 SDK 隐式重试，JSON 纠错最多一次。token 护栏依据已返回用量阻止后续请求，续跑预算重新计算。

## 组件 demo 的公共启动层（common/bootstrap.py）

s01–s17 的 `code.py` 不再各自复制「读 .env → 建客户端 → 取 MODEL_ID → input() 循环」，统一改为：

```python
sys.path.insert(0, str(Path(__file__).resolve().parent.parent))
from common.bootstrap import make_client, resolve_model, run_repl, print_last_text
client = make_client()        # 只建客户端，不检查 Key，测试可无 Key 导入
```

- `run_repl()` 在开始对话前调用 `require_credentials()`：没有有效 Key 时打印一行中文提示并以退出码 1 结束，不再抛 401 堆栈。
- 对话中的 401 / 403 / 404 / 429 / 网络错误由 `guard()` 翻译成一句话提示；不认识的异常照常抛出，便于排查。
- s12、s13、s15、s16、s17 结构特殊，只在入口处加了凭证检查并用 `guard()` 包住一轮对话，其余逻辑未动。
- 测试 `tests/test_demo_bootstrap.py` 会用占位 Key 逐个启动 17 个 demo，断言退出码为 1 且输出不含 Traceback。设置环境变量 `BLUEPRINT_SKIP_DOTENV=1` 可让启动层跳过读取 .env。

## mock 启发式的分档规则

`--mock` 模式的特征判断（`blueprint/mock.py`）把关键词分成两档：

| 档位 | 规则 | 例子 |
|---|---|---|
| 强信号 | 单独命中即判 yes | 删除、审核、知识库、每天、几分钟 |
| 弱信号 | 至少命中两个不同的词才判 yes，只命中一个判 unknown（待确认） | 团队、并行、流程、耗时、照片 |

「二期 / 未来 / 以后」类标记按**句子**判断：只有命中词所在的每一句都带标记，才判 later。
离线题库 `blueprint eval` 会守住下限：标准答案判「放弃」的组件，mock 不得判成必选或二期；`tests/test_mock_heuristics.py` 另外要求强信号明确的 s03、s07 仍能被选上。调关键词表时先跑这两处。

## 真实模型基线（2026-10-20，deepseek-v4-flash）

`blueprint eval --real` 只跑需求拆解阶段，统计 14 个特征与题库标准答案的一致率：

| 轮次 | 一致率 | 变化 |
|---|---|---|
| 初始 | 17/42 = 40% | paper-reader 全部为 None：模型把 features 的键写成了组件编号 s03…s17，校验放行后全部被当成 unknown |
| 修复键名归一化 + no/unknown 口径 | 27/42 = 64% | paper-reader 恢复到 10/14 |
| 收紧 later 规则 | 30/42 = 71% | 单次运行，模型有随机性，波动 ±2 题属正常 |
| 统一题库口径（工单题 unknown → no） | 35/42 = 83% | 见 `evals/README.md`；剩余差异集中在 multi_step / fixed_orchestration |
| 改写这两个特征的问句 | 38/42 = 90% | 工单、玩具两题全对；论文题剩 4 处，其中 multi_step 标准答案本身可再斟酌 |

对应改动：

- `blueprint/schema.py` 新增 `coerce_stage_output()`，在校验前把组件编号键映射回特征 id、裸字符串包成对象；`features` 现在把 14 个特征 id 列为必填，缺键会触发一次纠错重试。
- `blueprint/knowledge/prompts/extract.md`：明确键名规则；`no` 与 `unknown` 的口径（闭环已写清、特征不在其中 → no）；`later` 必须有原文依据。

（以下为口径统一前的分析，保留作记录）剩余差异主要来自题库本身的口径不一致：`ticket-triage/expected.json` 对未提及的特征多数标 `unknown`，而 `toy-theater/expected.json` 对同类情况标 `no`。模型按现在的提示词会偏向 `no`，于是在 ticket-triage 上「失分」。下一步应先统一三道题的标准答案口径，再继续调提示词；否则是在追一个自相矛盾的目标。另有两处提示：`must_be_unknown_or_pending` 用子串匹配（「孩子年龄」匹配不到「孩子的年龄段」），判定偏脆；`multi_step` / `fixed_orchestration` 模型倾向把「识别→生成→审核」读成固定多步流程，是否算 yes 需要在特征定义里说清。

完整运行一次正向方案（玩具剧场，含一次审稿打回重写）为 6 次调用、约 4 万 tokens；反向审计 2 次调用、约 1 万 tokens（2026-10-27 起反向默认走 agent，见「反向检查的 agent」）。两份真实产物已放在 `docs/examples/`。

## s13 / s15 的分节结构

两章的代码按 `# -- 小节 --` 切成了 `s13_agent_teams/s13_parts/pNN_*.py` 和 `s15_integrated_harness/s15_parts/pNN_*.py`，`code.py` 只剩文档字符串（含分节清单）和一个加载器：按文件名顺序把各分节 `exec` 进 `code.py` 自己的 `globals()`。

**为什么是执行进同一个命名空间，而不是 import 成包。** 拆分前统计：s15 有 28 个模块级可变状态、5 处函数内 `global` 写入；八个测试文件通过改写模块全局名注入假模型、假工具分发、假锁，s15 约 15 个名字、s13 约 20 个（`component.client = …`、`component.call_llm = …` 等）。拆成子模块后这些函数会绑定到子模块自己的全局，注入全部失效。共享同一个命名空间则与过去的单文件完全等价：函数的 `__globals__` 就是 `code.py` 的模块字典，测试与 s16 对 `host.X` 的读写照常生效，322 个测试一个断言都没改。

**读代码的方式**：先看 `code.py` 文档字符串里的分节清单（文件名、来源章节、作用），再打开对应的 `pNN_*.py`。分节文件头说明了它依赖前面的分节；回溯时按文件名顺序往前找即可。Traceback 会指向分节文件的真实行号。

**改代码的规则**：
- 新代码写进对应分节，不要写回 `code.py`；`tests/test_section_maps.py` 限制 `code.py` 不超过 150 行。
- 新增小节就新增一个 `pNN_` 文件并在 `code.py` 文档字符串里登记；标记 `# -- 小节 --` 仍要写在分节文件里，测试会核对。
- 分节之间仍然是全局名互相引用，顺序敏感：模块级代码只能引用更早的分节定义的名字，函数体内不受限制。
- 学生包（`tools/package_student.py`）会带上 `*_parts/`；单独拷走 `code.py` 无法运行。

s16 对 s15 的扩展已改为显式接口：s15 提供 `register_tool_extension(fn)`，在 `assemble_tool_pool()` 末尾依次执行；s16 注册 `add_workflow_tool`，只有宿主没有该接口时才退回包一层。

如果将来要把分节变成真正的 import 包，需要先把模块级状态收进一个 `RuntimeState` 对象并把测试改为对它打桩，这是一次独立重构。

## 反向检查的 agent（2026-10-27）

设计方案（含取舍理由）：<https://claude.ai/artifact/WPLjCAFcBH5r29d5Rw416S>。要点：

- **循环**（`blueprint/agent.py` 的 `run_agent`）：模型 → 工具调用 → 结果 → 模型。交卷靠一个 `finish` 工具，参数就是这一步的输出格式，本地用 `schema.validate` 和调用方给的 `check` 校验，不合格把错误作为工具结果退回，连续 3 次不合格算失败。模型只说话不调工具时提醒一次；最后一轮只提供 `finish`。模型返回的整段内容（含思考过程）原样放回历史；工具报错写进结果正文（DeepSeek 忽略 `is_error`）；单个结果超过 8000 字截断。每轮写进 `stages/<步骤>.transcript.jsonl`。
- **交卷参数为空**：参数很长时，接口偶尔会把格式出错的参数整个丢成 `{}`。遇到空参数，循环让模型改为在文字里输出交卷 JSON，修补后照常校验（见「交卷内容被弄丢时的补救」）。
- **模型调用**：`AnthropicRunner.step()` 带 `tools` 调一次模型，和 `complete()` 共用 `Budget`。没有 `step()` 的 runner（如 `MockRunner`）不走 agent。
- **反向检查的工具**（`blueprint/audit_agent.py`）：`list_dir`、`read_file`（一次最多 300 行）、`search`（纯 Python 正则，最多 50 条）、`component_card`、`select_components`（给了 PRD 时不提供）。全部只读；路径解析后必须在项目目录内；跳过扫描器的忽略目录和隐藏路径；`.env`、`.env.*`（`.env.example` 除外）、`*.pem`、`*.key` 等密钥文件一律拒绝；不读二进制和超过 200 KB 的文件。
- **交卷校验**：选型里必选、二期、待确认的组件，以及扫描器判为有 / 弱的组件，都要有结论（agent 要确认或推翻扫描结果）；没交结论的组件在 agent 模式下一律按 none 计，不沿用扫描结果。判 strong 或 weak 至少一条证据；证据文件必须是 agent 读过或搜到过的，行号不能越界。交卷后选型由代码按特征重算，agent 改不了规则结果。
- **退回**：`--fast`、`BLUEPRINT_AGENT=off`、runner 不支持、剩余调用次数不足 4 次、agent 失败（含接口报错）时走原来的扫描 + `infer` 写法，报告开头注明原因。`BudgetExceeded` 不退回，照常中止。
- **轮数与续跑**：最多 30 轮，并给后面的独立复核留 2 次调用。结论缓存在 `stages/audit_agent.json`，`--resume` 时源码、PRD 选型、模型、提示词都没变就沿用。
- **超时**：单次请求默认 120 秒，经中转的慢模型可能不够，用环境变量 `BLUEPRINT_TIMEOUT=300` 调大。命令行遇到接口超时或报错时提示续跑，不打印整段堆栈。
- **评测**：`eval` 离线时，`agent_only` 题（关键词陷阱）只检查报告结构；`eval --real-audit` 把题目复制到临时目录、去掉 `expected.json` 再检查（agent 会读文件，标准答案必须拿掉）。
- **服务商**（`tools/probe_tools.py`，2026-10-27）：DeepSeek v4-flash / v4-pro 单次、多轮、一次多个调用三项全过；模型中转（蚂蚁数科 MaaS，Anthropic 接口 `https://maas-api.antdigital.com/`）12 个对话模型 10 个通过，jev-1.13 只支持 OpenAI 协议，step-5-preview 走 Anthropic 接口整体报参数错误。智谱、Kimi 官方接口未测。
- **真实基线**（2026-10-27，deepseek-v4-flash，`eval --real-audit --repeat 3`）：四题 × 3 次 = 12 次全部判对，全部用上 agent。每次 4–9 次调用、1.0 万–2.7 万 tokens，读 1–4 个文件，远低于 40 次 / 150 万的上限。关键词陷阱两题快速扫描都判错（keyword-only 把 s03、s09 判 strong；no-keyword 把 s03 判 none），agent 都判对。12 次里有 3 次交卷参数为空，都由文字交卷接住。
- **自检发现的问题**（2026-10-27）：拿引擎检查自己时，选型为「放弃」的 s12 / s13 / s14 没让 agent 核实，报告沿用了扫描器的误报（引擎自己的知识表里满是 cron、mcp 等关键词），显示「有」。改为扫描器命中的组件也必须核实后，三项都被 agent 推翻；修复后 DeepSeek 四题再跑一遍全对。同一项目两次检查的特征判断（进而选型）会有出入，和正向推导一样是模型判断的波动。

## 新建产品的追问 agent（2026-10-27）

- **做法**（`blueprint/intake_agent.py`，提示词 `chat_intake_agent.md`）：用户每回一句，agent 先调 `check_coverage` 把六个维度各写一句，代码按固定规则判每个维度「已说明 / 用户不确定 / 缺」；再交 `finish`：`action=ask`（一个问题 + 最多 3 个快捷回答）或 `action=draft`（产品名 + 七小节需求草稿，格式同原来的整理提示词）。
- **能不能收尾由代码定**：目标、用户、核心闭环、边界四项都不是「缺」才允许 `draft`（用户说不确定也算处理过）；用户点「信息够了，帮我整理」或已问满 6 轮时只允许 `draft`。边界列为必须项，是因为真实测试里一句话写得长的想法被直接整理，红线一次都没问。
- **每次回复最多 3 轮模型调用**（`AnthropicChat` 的护栏 4 次 / 6 万 tokens 不变）。问题是工具参数，生成完再分段推送。快捷按钮 = 模型给的 + 固定的「不确定，先跳过」「信息够了，帮我整理」。
- **退回**：离线演示（`MockChat` 没有 runner）、runner 不支持工具、agent 失败时，这一轮走原来的固定三轮（`INTAKE_ROUNDS`）。
- **真实验收**（2026-10-27，deepseek-v4-flash，模拟用户脚本）：三道正向题的完整输入都不追问、直接出草稿（各 2 次调用）；只给第一句话、由另一个模型扮演用户回答时，三题都问 3 个问题（给谁用 → 过程 → 红线）后出草稿（10–14 次调用），草稿只整理用户说过的话，没说清的列进「还没想清楚」。
- 「加新需求」的追问、「回答问题」这期没动。

## 方案推导的 agent（2026-10-27）

- **顺序**：① 需求拆解 → ③ 规则选型（提前，只依赖 ①）→ ②+④ agent（`blueprint/plan_agent.py`，提示词 `plan_agent.md`）→ ⑤ 独立审稿，不过就带意见让 agent 重写一次。agent 能看到原始输入，可调 `component_card` 查组件、`check_design` 自检，最后 `finish` 交五要素 + 架构设计。结果用 `StageRunner.run_custom` 按输入签名缓存，`--resume` 可沿用。
- **`check_design`（纯代码）**：必须改（拦交卷）——工具 3–8 个、英文 snake_case 不重复、层级 ①–⑦；安全降级覆盖工具失败（任一行含「失败 / 不可用 / 报错 / 出错 / 异常」）、模型幻觉、超时、越权；有破坏性操作时至少一个 ask / deny 工具、权限要素有「默认拒绝 / 审批 / 确认」；`testing` 有单元测试和权限 / 安全边界测试；部署说明写了怎么启动、配置与密钥怎么外置。建议看看（只提醒）——系统提示词字数、是否提到每个工具；有副作用却 allow 的工具；必选组件在设计里有没有对应安排；设计里出现、原始输入没有的具体数值。
- **新增 `testing` 字段**（固定流程也有）：真实对比里 6 份第一版审稿全部因「可测试」整节缺失被判 high——审稿看的是设计 JSON，而方案文档里「可测试」那行原来是写死的一句话。`DESIGN_SCHEMA` 加了必填的 `testing`，两份设计提示词都要求写测试设计、启动方式和配置 / 密钥外置，并且原始输入没给的数值要标「（假设，待确认）」。
- **退回**：`BLUEPRINT_AGENT=off`、runner 不支持、剩余调用不足、agent 失败时走原来的 ② ④ 两步，方案开头注明原因。
- **费用护栏**：命令行和网页推导默认改为 40 次、150 万 tokens（和检查一致）。

## 试玩的 agent（2026-10-27 起，2026-10-28 改为默认打开）

- **默认打开**（2026-10-28 用户决定）：同学们用的模型五花八门，便宜模型未必守得住提示词里的规矩，而 agent 版的 deny / ask 由代码保证。设置 `BLUEPRINT_PLAY_AGENT=off` 才退回一次调用的写法；模型不支持工具调用时也会自动退回。10-27 曾因等待时间约 3 倍默认关闭过一天。
- **边跑边显示**：agent 在后台线程跑，每出一张卡片就推给界面（`_live_agent_events`）。实测「出个剧本」第 5 秒出第一张卡片、24.5 秒出回复；原写法要 9 秒才一次性出现。agent 一步都没走成就退回原写法；已经推出卡片后才出错，就只说明这一轮没演完，不重复演一遍。
- **做法**（`blueprint/playground.py` 的 `_agent_turn`，提示词 `chat_play_agent.md`、`chat_play_turn.md`、`chat_play_tool.md`）：Agent 以方案里的系统提示词为身份（看不到需求文档），方案工具清单里的每个工具注册成真工具。权限由挂在循环上的 `before_tool` 钩子（`permission`）在执行前处理：allow 放行，工具函数交给另一次模型调用扮演外部世界（看得到需求文档和对话）编结果；ask 不执行、记为「先问人」并告诉 Agent 确认前不能当作已完成；deny 不执行、记为「按规则拦下」。另有 `block_request` 让 Agent 声明按规则拒绝。回复可以直接说话（`run_agent` 的 `text_result`），也可以 `finish`。
- **卡片**：输入超过 40 字只显示开头（Agent 常把整份剧本、整段 JSON 当输入），完整内容仍交给结果模拟。
- **费用**：每条消息 Agent 最多 5 轮；网页试玩的护栏 16 次 / 20 万 tokens，剩余不足 2 次时不再模拟工具结果、直接写「没有模拟」，不报错。
- **退回**：`BLUEPRINT_PLAY_AGENT=off`、离线演示、模型不支持工具、agent 一步都没走成时，用原来一次调用编出整轮动作的写法（`_scripted_events`）。
- **真实对比**（2026-10-27，deepseek-v4-flash，玩具剧场 agent 方案）：「出个剧本」agent 9 次调用、30 秒，一次调用写法 1 次、9 秒；「照片上传云端」agent 2 次、5 秒，一次调用写法 1 次、3 秒。两种写法的卡片顺序和拦截结果基本一致；agent 的优势是 deny / ask 由代码保证、Agent 看不到需求文档，代价是等待时间约 3 倍。

## 循环的钩子与上下文压缩（2026-10-29）

引擎检查自己时的结论是 agent 循环缺 s04 钩子和 s08 压缩，两样都加在 `blueprint/agent.py` 的 `run_agent` 里。设计见上面的设计文档「收尾第 1 项」一节。

- **钩子**（`Hook`）：`before_tool(name, args)` 返回文字就拦下不执行、文字作为结果；`after_tool(name, args, content)` 返回文字就替换结果；`before_finish(result)` 返回错误列表就退回重交。触发顺序：进度日志（`describe`）→ 调用方的 `hooks` → 重复调用守卫；交卷时 schema 校验 → 调用方 `hooks` 的 `before_finish` → `check`。`check`、`describe` 参数保留，内部就是钩子。钩子只对已注册的工具触发，`finish` 和不存在的工具不经过它。
- **用在哪**：试玩的 deny / ask 从工具函数搬到了 `before_tool` 钩子上，工具函数只管模拟 allow 的结果。内置的重复调用守卫：同一工具、同样参数第 3 次调用直接拦下（第 2 次放行，因为第 1 次的结果可能已被收起）。
- **压缩**（`compact`）：每次调模型前统计历史里工具结果的总字数，超过 `COMPACT_AT`（240,000 字）就把最近 `KEEP_RECENT_ROUNDS`（2）轮以外的结果一次性换成一行「（已收起：<工具和参数>，原 N 字；需要时重新调用）」。只改用户消息里 tool_result 的正文，模型回复（含思考过程）和调用 / 结果的配对不动；说明比原文还长的短结果不收。一次收到底，是为了少让服务商的提示缓存失效。收起事件写进 transcript（`{"compacted": n, "chars": x}`），终端打一行进度。不做「让模型写摘要」那一层：多一次调用，还可能丢掉证据行号。
- **门槛为什么这么高**（2026-10-29 实测，deepseek-v4-flash，引擎检查自己，关 / 开各 2 次）：门槛设 48,000 字时每次检查收起 6 次，agent 记不住查过什么，工具调用从 22、29 次涨到 42、59 次，两次都用满 30 轮才被迫交卷；每收起一次服务商的提示缓存就失效一次，未命中缓存的输入从 4.1 万、5.6 万涨到 13.6 万、13.7 万 tokens。所以压缩只当防撑爆的保险：不压缩时工具结果最多攒到 15.3 万字，门槛定在 24 万字，正常检查碰不到；128k 上下文的模型也不会被撑爆。
- **用量没算缓存命中**：`Budget` 记的 `input_tokens` 是服务商返回的未命中部分，命中缓存的输入（上面实测每次 43 万–70 万 tokens）不计入费用护栏。命中部分单价低很多，但不是零。
- **不受影响的**：反向检查「证据必须读过」记在工具那边（`ProjectFiles.seen`），不看历史；交卷校验、费用护栏、退回逻辑不变。
- 测试：`tests/test_agent_runtime.py` 的「钩子」「收起旧的工具结果」两节。

## 特征判断的波动（2026-10-29）

同一份材料，模型逐题判断 14 个特征每次会有一两题不一样，选型跟着跳。按材料分两种处理，设计和实测见设计文档「收尾第 2 项」。

**有原文时取多数票**（正向推导、加新需求、对照 PRD 检查项目）：`blueprint/vote.py` 拿同一份原文另外独立判断两次特征，三票取多数。

- **计票**（`vote.majority`）：得票过半的取值胜出，依据沿用第一张投这个值的票（原判断优先）；三票各不相同判 unknown（进待确认）；某一票缺了这个特征按 unknown 算。
- **提示词**（`vote_features.md`）：特征问题那一节在运行时从 `extract.md` 截取（「## 特征问题」到「## 待确认清单」），改特征口径只改 `extract.md`。阶段名 `vote_features_1` / `_2`，`coerce_stage_output` 也会处理它们。
- **入口**：`run_plan` 和 `quick_reselect` 在需求拆解后投（`forward.vote_on_features`，两者共用缓存所以必须一致），`run_audit` 对 PRD 的拆解投。结果和改判记录存 `stages/vote_features.json`，续跑沿用。
- **不投票**：离线 mock、`--fast`、`BLUEPRINT_VOTE=off`、加新需求时所有特征都沿用上一版、剩余调用不足 10 次。
- **实测**（deepseek-v4-flash，`eval --real --repeat 3`）：准确率不变（单次 91%，取多数 90%），同一道题 3 次之间结果不一致的特征从 7/42 降到 3/42。代价是每次推导多 2 次小调用。

**没给 PRD 检查项目时沿用上次的判断**，不投票：

- **为什么不投票**：试过让另外两票看 agent 写的产品描述来判断。它们没读过代码，每次都和 agent 有 2–4 个特征不同，又彼此一致，于是把 agent 压了下去；产品描述本身每次也不一样，等于多了一个波动源。引擎检查自己 3 次，有分歧的特征从不投票时的 3/14（5 次）涨到 6/14。
- **做法**（`reverse.previous_features`）：输出目录里有同一项目上次 agent 检查的 `audit.json` 时，特征沿用上次的，选型按它算好交给 agent（走和 PRD 相同的路径，agent 只核实组件、不再判断特征，`select_components` 工具也不提供）。报告开头写明沿用的是哪天那次检查；`agent_stats.features_from` 记下最初那次的日期，连续沿用时不变。
- **不沿用**：`--rejudge`、`--resume`（续跑同一次检查）、给了 PRD、上次检查的是别的项目、上次是快速扫描或对照 PRD 的检查。
- 测试：`tests/test_vote.py`；`tests/test_agent_runtime.py` 的「沿用上次」三个测试。那里的剧本只写了 agent 一份判断，用 `BLUEPRINT_VOTE=off` 关掉投票。

## 交卷内容被弄丢时的补救（2026-10-29）

复查引擎自己时见过一次：agent 交卷参数被丢成 `{}`，改用文字交卷，又因为 `facts` 结尾漏了一个 `}` 被判「缺少 intent」；它接着又调 `finish`，参数又被丢掉，三次不合格退回快速扫描。设计见设计文档「收尾第 3 项」，都在 `blueprint/agent.py`：

- **修括号**（`parse_submission`）：文字里的交卷 JSON 从第一个能解析的左括号取起；闭合后多出的解释、围栏丢掉，到末尾没闭合就补齐右括号；再用 `hoist` 按 `result_schema` 把落错层的字段移回去（某层缺了 schema 规定的字段、而它落在下一层且那层 schema 不认它）。`hoist` 也作用于 `finish` 的参数。修出来的结果照样过 schema 和 `check`，修错了不会被放过。
- **报错带位置**：修不好时告诉模型 JSON 坏在第几个字、附近是什么。不再用 `extract_json` 退而取里层对象，那样报错会变成「缺少某字段」。
- **关掉 finish**：参数被丢空一次后不再提供 `finish`（只给调查工具；没有调查工具时只能留着 `finish`，因为历史里有工具调用时接口要求带工具定义），最后一轮的提示也改成要文字 JSON。
- 试玩的 `text_result`（直接回复使用者）不经过修括号。
- 测试：`tests/test_agent_runtime.py` 里用这次真实失败的形态做了回归。

**改页面：** 在 `web/` 里 `npm install` 一次；开发时另开终端跑 `python -m blueprint ui --no-browser`（或加 `--mock`），再在 `web/` 里 `npm run dev`，接口会转发到 8765 端口。改完 `npm run build`，把 `blueprint/web/static/` 的变化一起提交。CI 的 `web-build` 会重新构建并比对，忘了构建会失败。

- **assistant-ui 组件是复制进来的源码**：`web/src/components/assistant-ui/` 由 shadcn 注册表生成，已经改成中文并去掉了附件、语音、反馈、导出。升级时用 `npx shadcn add @assistant-ui/thread --overwrite` 会覆盖这些改动，先对比再合并。
- **布局**：应用式外壳（`web/src/App.tsx`），左侧固定栏放产品列表和设置，每页顶部一条窄工具栏（`common.tsx` 的 `TopBar`），内容区各自滚动。产品页左边是分组导航（`product.tsx` 的 `NAV`），对话类分区用 `components/chat/chat-pane.tsx` 铺满右侧高度；窄屏时侧边栏收进菜单按钮，分组导航变成横向标签。整体尺寸靠 `index.css` 里 `html { font-size: 106.25% }` 等比放大（字号、间距、按钮、栏宽都以 rem 计）；新写的尺寸用 Tailwind 刻度或 rem，别写死 px，否则不会跟着放大。
- **字体**：西文 Geist，中文小米 MiSans 可变字体（npm 包 `misans`，按字符范围切片、用到才下载）。这个包的切片沿用小米官方网页字体的范围，漏了全角符号（？～％、全角数字等），`web/src/assets/fonts/misans-vf-fullwidth.woff2` 是从官方 MiSansVF.ttf 用 fontTools 切出的这部分，在 `index.css` 里以同一字体名补上。升级 `misans` 后检查切片是否已经包含这些字，包含就删掉补丁。
- **对话无状态**：前端每次把整段对话发给服务端，`chat.py` 从对话里推出走到哪一步（第几轮追问、第几题、用户按了哪个快捷按钮），所以编辑、重新生成都不会错位。走到哪一步由代码决定，模型只负责措辞：追问、整理成需求草稿、「帮我想想」给几个方向。
- **快捷按钮按原文识别**：`chat.py` 的 `FINISH_INTAKE`、`SKIP_INTAKE`、`HELP`、`SKIP`、`SAVE` 是按钮文字，也是服务端判断的依据；回答问题开场的两个按钮写在 `web/src/pages/product.tsx` 的 `OPENING_CHIPS`，改文字要两边一起改。
- **确认卡片**：服务端发 `tool` 事件，前端用 assistant-ui 的 human tool 渲染成卡片（`web/src/components/chat/tool-cards.tsx`），用户点确认后调用普通接口建产品或保存回答，卡片原地变成推导进度。
- **对话存在浏览器本地**：`web/src/components/chat/chat-storage.ts` 用 assistant-ui 的 `thread.export()` / `import()` 把对话和快捷按钮存进 localStorage，切换标签、刷新都能接着聊。新建产品一份（键 `intake`）；回答问题按「产品 + 这组问题的指纹」各一份，方案一变问题就变，旧记录自动删除。卡片一确认（流程走完）就删记录；「重新开始」按钮清空重来。只存在这台电脑的这个浏览器里。
- **旧浏览器**：Tailwind v4 需要 Safari 16.4 / Chrome 111 及以上。`web/index.html` 检测不支持时直接显示升级说明，不挂载界面。
- **浏览器测试**：Chrome 和 WebKit（Playwright，与 Safari 同引擎）都走通过完整流程；真 Safari 的自动化需要在 Safari 设置里打开「允许远程自动化」（`sudo safaridriver --enable`），没开时可以用 Playwright WebKit 代替。
- **回答写进 PRD**：`workspace.record_answers` 追加到 PRD 第 6 节末尾，不升版（回答是补全，不是新需求），并记一条迭代记录；之后照常续跑推导。
- **只认本机**：服务只监听 `127.0.0.1`；请求的 `Host` 必须是本机地址，POST 还要求 `Content-Type: application/json` 且 `Origin`（若有）是本机，挡住别的网站借浏览器对本机服务发请求。API Key 写进 `.env` 后，页面只拿到掩码。
- **推导放后台线程**：`JobManager` 一个产品同时只跑一个任务；进度来自 `StageRunner` 的 `log` 回调，页面按日志里的 ①–⑤ 判断阶段。改 `pipeline.py` 的日志格式时同步看 `web/src/components/job-progress.tsx` 的 `stageStates`。任务只存在内存里，界面重启后丢失，但已完成的阶段在 `stages/` 里，点「生成方案」会续跑。
- **报错转述**：`jobs.friendly_error` 按异常类名把 SDK 报错翻译成大白话，推导任务和对话都用它。
- **模型配置共用一份**：服务商列表、读写 `.env`、测试连接在 `blueprint/providers.py`，终端向导和界面都用它。`write_env` 只改三项模型配置，`.env` 里其他行原样保留。
- **示例指纹不含对话提示词**：`tools/refresh_examples.py` 的指纹只算推导管线的提示词，改 `chat_*.md` 不会让示例显示过期。
- **大白话问题**（`blueprint/plain.py`）：组件类待确认问题用 `FEATURE_PLAIN` 里手写的大白话版本（新增特征时要补一条，`tests/test_plain_questions.py` 会检查）。模型写的问题在网页推导完后多调一次模型（提示词 `chat_plain_questions.md`）改写并分流：问提出想法的人的进「回答问题」，只有工程师能判断的进「技术备注」和交接包。需求拆解和架构设计常各问一遍同一件事，改写时模型用 `duplicate_of` 标出重复，界面只问一次，被并掉的原问题写回 PRD 时一起带上。结果按编号存在 `stages/chat_plain_questions.json`，原问题列表存在同目录的 `.source.json`，按原文匹配；改写失败或用命令行推导时回退到原问题。`方案.md` 仍是原问题，给开发者看。写回 PRD 时问题带上「（原问题：…）」，下一轮推导能对上。
- **交接包**（`blueprint/handoff.py`，网页「导出交接包」或 `blueprint handoff`）：不调模型，打包 PRD、方案、迭代记录、skeleton/（去掉 .env 和环境目录）、交接说明、给 AI 编程工具的提示词，以及必选组件的参考实现。参考实现之间有运行时依赖（s15 加载 s09，s16 加载 s15），记在 `REFERENCE_DEPS`；`tests/test_handoff.py` 扫描源码守护这张表，并在解压后的目录里逐个加载每个 code.py。
- **「帮我想想」**：选项格式是「A. 做法 —— 代价」，用户只回一个字母时 `chat._resolve_option` 只记破折号前的做法。
- **加新需求**（`chat.revise_events`，提示词 `chat_revise_*.md`）：最多追问一轮，整理成「一句话标题 + 需求正文」草稿；确认后走 `revise_workspace(..., warn_undigested=False, source="网页界面·加新需求")`，固定完整重推（不用 `--quick`，免得小白看到旧方案）。网页用户没有 AI 工具去「消化」新需求，新需求留在 PRD 第 7 节、由推导直接读取，所以不写「还没消化」的提醒。任务返回选型变化，页面推导完跳到「版本历史」。
- **版本历史**：`workspace.version_table` 读 PRD 的版本表，`workspace.log_entries` 读迭代记录；网页把命令行步骤、给 AI 的提醒这类行藏掉（`web/src/pages/product-history.tsx` 的 `HIDDEN`），选型变化画成标签。改迭代记录的措辞时同步看这里的解析。`bump_prd` 升版时除了 `prd/V{n}.md` 还会留 `prd/V{n}.plan.json`，当时的方案也能回看。
- **PRD 第 2–5 节自动整理**（`blueprint/prd_fill.py`，提示词 `chat_prd_fill.md`）：网页里每次推导或升版后，根据第 1 节原话、第 6 节回答、第 7 节新需求和需求拆解的事实写这四节。只写仍是模板、或带 `AUTO_MARK` 的小节，人或 AI 工具写过的不动。这四节是**产物不是输入**：`run_plan` / `quick_reselect` 先用 `workspace.strip_auto_sections` 去掉它们再推导，否则里面的「待确认」会被再拆成问题（真实模型实测：不去掉时一轮从 11 问涨到 22 问）。
- **加新需求时稳住选型**（`blueprint/stability.py`，提示词 `revise_affected.md`）：升版重推前先判断新需求涉及哪些特征（1 次小调用，mock 用关键词），没涉及的特征沿用上一版判断（`run_plan(feature_overrides=...)`，理由写「沿用 V{n} 的判断」），迭代记录写「重新判断：……；其余沿用 V{n} 的判断」。`revise_workspace(stabilize=False)` 可关闭，命令行 revise 默认也开启。
- **问题优先级**：大白话改写时模型给每个用户问题标 priority（1 = 不答就没法动手，最多 5 个），按优先级稳定排序，关键问题在界面带「关键」标签、超过 8 个时其余折叠，回答问题的开场白提示「答完前 N 个就可以先保存」。
- **累计用量**（`blueprint/usage.py`）：`plan.json` 里的 budget 只是最近一轮推导，断点续跑沿用的阶段不计费。网页把每一轮真实发生的调用记进工作区 `usage.json`：推导和加新需求任务（含大白话改写、PRD 整理）在 `finally` 里记，中途失败也算；回答问题和加新需求的对话由 `server.metered` 在回复发完或用户中途停止时记。新建产品时的对话还没有工作区，不计入。产品页底部显示累计数，没有 `usage.json` 的老产品回退显示最近一轮。
- **对话结束后收起输入框**：确认卡片一提交，`thread.aui.tsx` 用 `Finished` 槽位替换输入框和快捷按钮（默认一句「这段对话已经完成」；新建产品页换成「再新建一个产品」）。
- **试玩**（`blueprint/playground.py`，提示词 `chat_play.md`、`chat_play_intro.md`）：用户扮演产品的使用者，模型按方案的系统提示词、工具清单、安全规则扮演这个 Agent。定位是演示，不是产品也不是原型：不生成代码、不导出、不进交接包，README 三方边界里写明了。每轮一次 `complete_json`，返回模拟动作（`tool` 只能用工具清单里的工具，`ask_owner` 要先问人，`blocked` 按规则拦下）和回复；服务端以 `data` 事件发给前端，前端渲染成数据卡片（不是 human tool，不会触发「对话结束」），并把每步的 `wire` 文字随对话发回，下一轮模型才知道之前调过什么。括号里的旁白当作外面已经发生的事。开场（扮演谁、三四句可以先说的话）按方案指纹缓存在 `stages/chat_play_intro.json`，提示词、工具或安全规则变了才重新生成；对话本地存储也按这个指纹分。回复下方的「这里不对」记在浏览器本地，「带去加新需求」把它们拼成一段话放进「加新需求」的输入框（sessionStorage 传递），用户再发送。
- **当前范围**：模型设置、产品列表、对话式新建产品、查看方案、对话式回答待确认问题、试玩、导出交接包、对话式加新需求、版本历史。检查代码骨架（verify）、检查外部项目（audit）还没做，仍走终端向导或命令行。
- 测试：`tests/test_web_ui.py`（接口与对话流程）、`tests/test_chat_flow.py`（步骤推算、写回 PRD、真实模型路径用假客户端）、`tests/test_usage.py`（累计用量）、`tests/test_playground.py`（试玩），全部离线，不读写真实 `.env`。
