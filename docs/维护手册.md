## 常用命令

在引擎根目录运行：

```sh
.venv/bin/python -m blueprint plan idea.md -o out/my-plan
.venv/bin/python -m blueprint audit /目标项目路径 --prd prd.md -o out/my-audit
.venv/bin/python -m blueprint plan idea.md -o out/my-plan --resume
.venv/bin/python -m blueprint eval
.venv/bin/python -m blueprint eval --real
.venv/bin/python -m pytest -q

# 产品循环（blueprint/workspace.py）：工作区固定在 out/<产品名>/
.venv/bin/python -m blueprint init "产品名" "一句话点子" --plan
.venv/bin/python -m blueprint revise out/产品名 "新需求" [--no-plan]
.venv/bin/python -m blueprint verify out/产品名
```

`BLUEPRINT_OUT` 环境变量可以把输出根目录从 `out/` 改到别处（测试用）。`revise` 的做法是：快照 `PRD.md` 到 `prd/V{n}.md`、把「当前版本」升一号、在版本记录表追加一行、把新需求原文追加到「新增需求（待消化）」一节，然后以新 PRD 为输入 `--resume` 重推方案，并把前后 `plan.json` 的组件决策差异写进 `迭代记录.md`。`verify` 就是 `audit skeleton/ --prd PRD.md -o verify/` 的快捷方式，另加一条迭代记录。

`--mock` 为离线占位输出；`--model` 覆盖模型 ID；`--max-calls` 和 `--max-tokens` 限制新一轮运行的调用次数和 token 用量，不是金额硬上限。

## 修改规则与模型

- **改规则**：同步修改选型规则、特征表和 `evals/forward/*/expected.json`，再运行离线评估。
- **加组件**：补齐组件说明、特征映射、扫描信号及测试；不要仅凭关键词数量认定功能完整。
- **改提示词**：模板使用 `str.format`，字面花括号写成 `{{ }}`。改完需做真实输出质量检查，不能只看 JSON 是否合法。
- **改模型**：维护者在 `.env` 配置 `ANTHROPIC_API_KEY`、`MODEL_ID`，自定义 Anthropic-compatible 网关使用 `ANTHROPIC_BASE_URL`。环境变量优先于 `.env`。不要将密钥复制到手册或分发包。
- **失败续跑**：同一任务使用同一输出目录加 `--resume`。缓存核对输入、源码摘要、模型、提示词、schema 和上游结果，变更或损坏时重跑；写入使用原子替换。

## 验证边界

- 离线题库覆盖 3 个正向案例和 2 个反向案例；`eval --real` 当前只测正向需求拆解，完整方案和反向报告仍需真实验收。
- 扫描为正则启发式；业务代码命中至少 2 个文件或 4 行为 strong，1 个文件为 weak。文档和测试描述不计为实现，扫描跳过符号链接和依赖目录。
- 静态分数不能证明能力已集成，也不能替代运行测试；非 Python 入口与调用关系识别有限。
- 正向审稿失败会重写一次；审稿是同一模型的另一次调用。反向复核的输入覆盖仍需加强，尤其是用户 PRD 与反推意图不一致时。
- 真实请求超时 120 秒，关闭 SDK 隐式重试，JSON 纠错最多一次。token 护栏依据已返回用量阻止后续请求，续跑预算重新计算。

```sh
python3 tools/package_student.py
```

生成 `dist/agent-blueprint-student.zip`。脚本按允许清单收集教学内容；未列入的本机文件不打包。包括 `.env.example`、`setup.sh` 和可移植的 `.vscode/` 配置，不包括真实 `.env`、`.venv/`、Git、缓存和 `out/`。

修改内容后重新生成压缩包；若增加了需要分发的文件类型或目录，同步调整脚本清单。分发前在解压副本运行离线评估、测试，并检查 Markdown 链接。MIT 许可证必须随包保留。

## 组件 demo 的公共启动层（common/bootstrap.py）

s01–s17 的 `code.py` 不再各自复制「读 .env → 建客户端 → 取 MODEL_ID → input() 循环」，统一改为：

```python
sys.path.insert(0, str(Path(__file__).resolve().parent.parent))
from common.bootstrap import make_client, resolve_model, run_repl, print_last_text
client = make_client()        # 只建客户端，不检查 Key，测试可无 Key 导入
MODEL = resolve_model()       # MODEL_ID 缺省时回落到 DEFAULT_MODEL
```

- `run_repl()` 在开始对话前调用 `require_credentials()`：没有有效 Key 时打印一行中文提示并以退出码 1 结束，不再抛 401 堆栈。
- 对话中的 401 / 403 / 404 / 429 / 网络错误由 `guard()` 翻译成一句话提示；不认识的异常照常抛出，便于排查。
- s12、s13、s15、s16、s17 结构特殊，只在入口处加了凭证检查并用 `guard()` 包住一轮对话，其余逻辑未动。
- 测试 `tests/test_demo_bootstrap.py` 会用占位 Key 逐个启动 17 个 demo，断言退出码为 1 且输出不含 Traceback。设置环境变量 `BLUEPRINT_SKIP_DOTENV=1` 可让启动层跳过读取 .env。

## mock 启发式的分档规则

`--mock` 模式的特征判断（`blueprint/mock.py`）把关键词分成两档：

| 档位 | 规则 | 例子 |
|---|---|---|
| 强信号 | 单独命中即判 yes | 删除、审核、知识库、每天、几分钟 |
| 弱信号 | 至少命中两个不同的词才判 yes，只命中一个判 unknown（待确认） | 团队、并行、流程、耗时、照片 |

「二期 / 未来 / 以后」类标记按**句子**判断：只有命中词所在的每一句都带标记，才判 later。
离线题库 `blueprint eval` 会守住下限：标准答案判「放弃」的组件，mock 不得判成必选或二期；`tests/test_mock_heuristics.py` 另外要求强信号明确的 s03、s07 仍能被选上。调关键词表时先跑这两处。

## 默认模型只有一处事实来源

`blueprint/llm.py` 的 `DEFAULT_MODEL`、`common/bootstrap.py`、`.env.example`、`scaffold/` 与 `tools/wizard.py` 的 Anthropic 默认模型必须一致，由 `tests/test_config_consistency.py` 守护。改默认模型时把这几处一起改，测试会指出漏掉的文件。pytest 已锁定在 `requirements.txt`，`bash setup.sh` 之后可直接运行测试。

## 真实模型基线（2026-10-20，deepseek-v4-flash）

`blueprint eval --real` 只跑需求拆解阶段，统计 14 个特征与题库标准答案的一致率：

| 轮次 | 一致率 | 变化 |
|---|---|---|
| 初始 | 17/42 = 40% | paper-reader 全部为 None：模型把 features 的键写成了组件编号 s03…s17，校验放行后全部被当成 unknown |
| 修复键名归一化 + no/unknown 口径 | 27/42 = 64% | paper-reader 恢复到 10/14 |
| 收紧 later 规则 | 30/42 = 71% | 单次运行，模型有随机性，波动 ±2 题属正常 |
| 统一题库口径（工单题 unknown → no） | 35/42 = 83% | 见 `evals/README.md`；剩余差异集中在 multi_step / fixed_orchestration |
| 改写这两个特征的问句 | 38/42 = 90% | 工单、玩具两题全对；论文题剩 4 处，其中 multi_step 标准答案本身可再斟酌 |

对应改动：

- `blueprint/schema.py` 新增 `coerce_stage_output()`，在校验前把组件编号键映射回特征 id、裸字符串包成对象；`features` 现在把 14 个特征 id 列为必填，缺键会触发一次纠错重试。
- `blueprint/knowledge/prompts/extract.md`：明确键名规则；`no` 与 `unknown` 的口径（闭环已写清、特征不在其中 → no）；`later` 必须有原文依据。

（以下为口径统一前的分析，保留作记录）剩余差异主要来自题库本身的口径不一致：`ticket-triage/expected.json` 对未提及的特征多数标 `unknown`，而 `toy-theater/expected.json` 对同类情况标 `no`。模型按现在的提示词会偏向 `no`，于是在 ticket-triage 上「失分」。下一步应先统一三道题的标准答案口径，再继续调提示词；否则是在追一个自相矛盾的目标。另有两处提示：`must_be_unknown_or_pending` 用子串匹配（「孩子年龄」匹配不到「孩子的年龄段」），判定偏脆；`multi_step` / `fixed_orchestration` 模型倾向把「识别→生成→审核」读成固定多步流程，是否算 yes 需要在特征定义里说清。

完整运行一次正向方案（玩具剧场，含一次审稿打回重写）为 6 次调用、约 4 万 tokens；反向审计 2 次调用、约 1 万 tokens。两份真实产物已放在 `docs/examples/`。

## s13 / s15 的分节结构

两章的代码按 `# -- 小节 --` 切成了 `s13_agent_teams/s13_parts/pNN_*.py` 和 `s15_integrated_harness/s15_parts/pNN_*.py`，`code.py` 只剩文档字符串（含分节清单）和一个加载器：按文件名顺序把各分节 `exec` 进 `code.py` 自己的 `globals()`。

**为什么是执行进同一个命名空间，而不是 import 成包。** 拆分前统计：s15 有 28 个模块级可变状态、5 处函数内 `global` 写入；八个测试文件通过改写模块全局名注入假模型、假工具分发、假锁，s15 约 15 个名字、s13 约 20 个（`component.client = …`、`component.call_llm = …` 等）。拆成子模块后这些函数会绑定到子模块自己的全局，注入全部失效。共享同一个命名空间则与过去的单文件完全等价：函数的 `__globals__` 就是 `code.py` 的模块字典，测试与 s16 对 `host.X` 的读写照常生效，322 个测试一个断言都没改。

**读代码的方式**：先看 `code.py` 文档字符串里的分节清单（文件名、来源章节、作用），再打开对应的 `pNN_*.py`。分节文件头说明了它依赖前面的分节；回溯时按文件名顺序往前找即可。Traceback 会指向分节文件的真实行号。

**改代码的规则**：
- 新代码写进对应分节，不要写回 `code.py`；`tests/test_section_maps.py` 限制 `code.py` 不超过 150 行。
- 新增小节就新增一个 `pNN_` 文件并在 `code.py` 文档字符串里登记；标记 `# -- 小节 --` 仍要写在分节文件里，测试会核对。
- 分节之间仍然是全局名互相引用，顺序敏感：模块级代码只能引用更早的分节定义的名字，函数体内不受限制。
- 学生包（`tools/package_student.py`）会带上 `*_parts/`；单独拷走 `code.py` 无法运行。

s16 对 s15 的扩展已改为显式接口：s15 提供 `register_tool_extension(fn)`，在 `assemble_tool_pool()` 末尾依次执行；s16 注册 `add_workflow_tool`，只有宿主没有该接口时才退回包一层。

如果将来要把分节变成真正的 import 包，需要先把模块级状态收进一个 `RuntimeState` 对象并把测试改为对它打桩，这是一次独立重构。

## 2026-10-20 第二轮加固

- **题库口径**：`evals/README.md` 定义了 yes / later / no / unknown 的统一口径和两个易判错特征的边界；工单题按此改为 `no`。改题库时先读它。
- **输出截断**：`AnthropicRunner` 遇到 `stop_reason == max_tokens` 会自动把 max_tokens 加倍重试一次，再失败才报错并给出环境变量建议。格式错误的纠错重试仍只有一次，两类重试互不占用。
- **JSON 提取**：`extract_json` 会从每个左花括号位置尝试，模型在 JSON 前输出带花括号的解释不再导致失败。
- **revise --quick**：只跑需求拆解和规则选型（1 次调用），不重做设计与审稿；`方案.md`、`plan.json` 保持上一版。需求拆解结果进缓存，之后 `plan --resume` 直接沿用。
- **未消化提醒**：`revise` 和 `verify` 会检查 PRD「新增需求（待消化）」一节是否还留着上一轮的版本块，有就在终端和 `迭代记录.md` 里警告。消化的判定标准是该节下不再有 `### V{n}（` 开头的块。
- **向导**：`tools/wizard.py` 按命令打开对应文件（init/revise 开方案，verify 开差距报告），不再取 out/ 下最新的 .md。
- **章节 README**：每章末尾注明必须在仓库根目录运行，`code.py` 依赖 `common/`。
