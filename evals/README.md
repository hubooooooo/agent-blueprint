# 题库口径

`forward/*/expected.json` 是特征判断与组件选型的标准答案，`blueprint eval` 和 `eval --real` 都对照它。三道题必须用同一套口径，否则提示词往哪边调都会在另一题失分。

## 特征取值口径

| 取值 | 什么时候用 | 例子 |
|---|---|---|
| `yes` | 输入明确需要，或产品闭环里必然包含 | 工单题「所有自动回复要留审计记录」→ audit_needed |
| `later` | 原文有「未来 / 二期 / 以后」字样 | 玩具题「未来希望记住孩子的年龄」→ cross_session_memory |
| `no` | 输入已经把闭环说清楚，这个特征不在闭环里，也与产品形态明显无关 | 工单题没有任何跨会话个性化 → cross_session_memory=no |
| `unknown` | 特征可能在闭环里，但要不要这个机制取决于输入没给的信息（规模、频率、时延） | 论文题「长会话 / 日志量」取决于一次读几篇 → long_sessions=unknown |

两个容易判错的特征：

- `multi_step`（s05 任务规划）：问的是「需不需要跟踪进度的计划」。一次交付内部固定调用三个工具不算多步任务；只有输入提到「进度 / 阶段 / 多轮推进」才判 yes。
- `fixed_orchestration`（s16 工作流运行时）：只有输入把流程写成明确的固定阶段序列（论文题「完整流程：上传→翻译→标注→…」）才判 yes；描述的是产品体验或含模型分支决策的流程（工单题「能回答的直接回复，不能的升级」）判 no。

## 改题库时

1. 改完 `features` 后，`components` 必须是 `select_components(features)` 的输出，`blueprint eval` 的「规则回归」会校验。
2. `must_be_unknown_or_pending` 里的词用子串匹配待确认清单，写短一点（「年龄」优于「孩子年龄」）。
3. 跑一次 `blueprint eval --real`，把一致率记进 `docs/维护手册.md` 的基线表。
